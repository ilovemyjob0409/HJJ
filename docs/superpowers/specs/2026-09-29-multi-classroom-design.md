# 多教室（多租戶）設計

日期：2026-09-29。目標：MUP 從「一間教室專用」改成「一個系統裡切分多間教室」，讓作者可以把系統免費給附近的補習班試用（由作者手動開通），之後再商業化。

## 使用者定案決策

1. **教室＝一個獨立客戶**（一間補習班或機構）。教室之間的資料完全不互通，沒有總校／分校的階層。
2. **登入順序是教室代碼 → 帳號 → 密碼。** 帳號只在教室內唯一，同一個人在兩間教室就是兩個獨立帳號。一個帳號只屬於一間教室，而且只有一種身分（行政、老師或學生，沿用現行做法）。
3. **新教室由平台管理員（作者）手動開通。** 不做自助註冊，也不做金流。目前不分訂閱等級。
4. **所有功能模組化**，由各教室的行政在「教室設定」自行開關。模組清單見下方〈模組〉一節。
5. **技術做法採方案一**：同一個資料庫，每張表加教室 ID，由程式層的統一過濾器隔離資料。不採用 schema-per-tenant 或每間教室一套部署。
6. **平台管理員看不到任何教室的學生個資。** 平台後台只顯示人數等統計。
7. **品牌**：登入後左上角顯示教室 logo，沒有 logo 時顯示教室名稱；登入頁和頁尾保留小字「MUP」。
8. **分三階段做，各階段可獨立上線。** 三階段全部完成後，才開第二間教室。

## 名詞

- **教室（Classroom）**：租戶。欄位有代碼（code）、名稱、logo、狀態（啟用或停用）、已啟用的模組、建立時間。
- **教室代碼**：英文簡稱，是「選教室」用的識別，不是密碼。建立後不可改，全系統唯一。規則如下：
  - 只能用英文小寫 a–z、數字 0–9、連字號 `-`；不能以連字號開頭或結尾，也不能連續兩個連字號。
  - 長度 3–20。
  - 不分大小寫：輸入時先去掉前後空白再轉小寫，存與比對都用小寫。
  - 保留字不能當代碼：`admin`、`platform`、`api`、`www`、`login`、`logout`、`mup`、`test`、`static`、`public`。
  - 這套規則同時符合 DNS 子網域格式，將來改成 `<代碼>.<網域>` 時可以直接沿用。
  - 現有資料所屬教室（作者的教室）的代碼是 **`hjjdaya`**（作者指定 HJJDAYA，正規化成小寫）。
- **平台管理員（PlatformAdmin）**：獨立的表與獨立的登入，不屬於任何教室。

## 資料結構

- 新增 `Classroom` 與 `PlatformAdmin` 兩張表。
- 現有 47 個 model 全部加上 `classroomId`，不可為 null，並建外鍵與索引。
  - 附屬表也要加，例如 `BillPayment`、`ClassAttendance`、`PointTransaction`。這樣過濾器可以對每一張表套同一套規則，不必靠上層資料間接推斷。
  - 常用查詢的複合索引以 `classroomId` 開頭。
- 以下「全系統唯一」改成「教室內唯一」：

| 原本 | 改為 |
|---|---|
| `User.email @unique` | `@@unique([classroomId, email])` |
| `Student.studentNumber @unique` | `@@unique([classroomId, studentNumber])` |
| `ClosedDay.date @unique` | `@@unique([classroomId, date])` |
| `SubjectColor.subject @unique` | `@@unique([classroomId, subject])` |
| `ActivityCategory.name @unique` | `@@unique([classroomId, name])` |
| `BillingSetting` 單列（`id = "main"`） | 每間教室一列（`classroomId @unique`） |

- 仍維持全系統唯一：隨機 token（`FamilySwitchToken.token`）、`Bill.seasonPassId` 等以 id 為基礎的唯一鍵。
- **國定假日**：每日同步改成逐間教室寫入。各教室刪除某個假日，只影響自己。
- **Supabase Storage**：活動照片的路徑前綴加上 `classroomId/`。

## 隔離機制（統一過濾器）

- **請求情境**：用 AsyncLocalStorage 保存「目前教室 ID」。
  - 現有每個 API route 開頭都會呼叫授權檢查（`requireAdmin` 或 `getServerSession` 等）。這些檢查改成一組共用 guard，在驗證 session 之後把教室 ID 放進情境。
  - Server component 頁面走同一組 guard。
- **Prisma 擴充（`$extends`）**：對所有租戶 model 自動處理教室 ID。
  - 讀取、更新、刪除、計數、彙總：自動加上 `where.classroomId = 目前教室`。
  - 建立（含 `createMany`）：自動寫入 `classroomId`。
  - `findUnique` 也加上 `classroomId` 條件（Prisma 7 支援在唯一查詢裡加非唯一欄位）。
- **fail-closed**：租戶 model 的查詢若在沒有教室情境下執行，一律拋錯，不會回傳全部資料。
- **明確的例外入口**：
  - `withClassroom(id, fn)`：給排程或系統工作在指定教室下執行。
  - `asPlatform(fn)`：給平台後台與登入流程做跨教室查詢，例如依代碼找教室、統計人數。
  - 程式碼審查時要特別檢查這兩個入口的每一處使用。
- **巢狀寫入**：因為 `classroomId` 不可為 null，巢狀 create 若漏帶教室 ID，會在型別或資料庫層失敗，由測試抓出，不會默默寫進錯的教室。
- **原生 SQL**：3 處 `$executeRaw`，分別在 `billingBatchService`、`billEditService`、`classService`，不經過擴充，必須手動加上 `classroomId` 條件並加測試。`resetDb` 是測試工具，不受影響。
- **互動式 transaction**：沿用擴充後的 client，tx 也會被過濾。實作時要以測試確認。

## 登入與權限

- 登入頁有三個欄位：教室代碼、帳號、密碼。
  - 瀏覽器用 localStorage 記住上次的代碼（包 try/catch，讀取失敗就退回空白）。
  - `/login?c=<代碼>` 會自動帶入代碼（例：`/login?c=hjjdaya`）。
- 任一欄位錯誤，一律只顯示「教室代碼、帳號或密碼錯誤」。
- 教室停用時：帳號密碼正確仍拒絕登入，顯示「此教室已停用」。已登入的人最晚 1 分鐘內失效（教室狀態有 60 秒快取）。
- JWT 與 session 帶 `classroomId`、`role`。舊的 JWT 沒有 `classroomId`，一律視為未登入，上線時所有人重新登入一次。
- 手足帳號切換（switch token）只能切到同一間教室的帳號。
- 平台管理員：登入頁在 `/platform/login`，session 標記為平台身分，不能進 `/admin`、`/teacher`、`/student`，教室帳號也不能進 `/platform`。

## 模組

**基本功能（不可關閉）**：首頁、學生管理、老師管理、班級管理、點名（含掃碼）、出席紀錄、週課表、通知（鈴鐺與推播）、手足帳號切換。

**可選模組**：

| 代號 | 模組 | 範圍 |
|---|---|---|
| `LEAVE_MAKEUP` | 請假與補課 | 學生請假／補課申請、補課須知、行政請假管理、老師可補課時段 |
| `SUBSTITUTE` | 代課安排 | 老師請假／調課、行政指派代課 |
| `TUTORING` | 個別輔導 | 預約日曆、額度、出缺勤總表，以及相關的收費與未補堂數 |
| `GO_HALL` | 弈廳 | 場次、報名、堂票和季票、弈廳收費單、掃碼點名裡的弈廳場次 |
| `BILLING` | 收費 | 開單、繳費、學生繳費頁、首頁待繳卡 |
| `POINTS` | 集點與獎品 | 給點、集點卡、獎品兌換 |
| `ACTIVITIES` | 活動專區 | 活動、報名、相簿 |
| `FAQ` | 常見問題 | 行政維護、學生查看 |

模組關閉時的規則：
- 選單不顯示；頁面被導回首頁；API 回 403 `MODULE_DISABLED`。
- 其他頁面上屬於該模組的區塊一併隱藏，例如首頁的弈廳資格卡、待繳卡、未補堂數中的個輔部分、收費裡的個輔帳單與弈廳帳單。
- 資料保留，重新開啟即恢復。
- 背景排程（提醒、推播）只對有開啟該模組的教室執行。

新教室預設開啟 `LEAVE_MAKEUP` 與 `FAQ`，其他由開通時勾選。現有教室（`hjjdaya`）搬遷時全部模組開啟。模組名稱自訂（例如「MPM&PLUS」）留到下一版；在那之前，現有教室維持現行叫法，新教室用通用名稱。

## 平台後台（`/platform`）

- **教室清單**：名稱、代碼、狀態、建立日期、學生數、老師數。
- **新增教室**：代碼、名稱、logo（選填）、第一個行政帳號（姓名、email、初始密碼）、模組勾選。
- **教室詳情**：改名稱、換 logo、停用或恢復、新增行政帳號、重設行政帳號密碼、開關模組。
- 平台管理員帳號用一次性指令（script）建立，不做「新增平台管理員」畫面。
- 不提供進入教室查看學生資料的功能。

## 教室設定（行政）

- 行政選單新增「教室設定」。
- 可以改名稱、換 logo；代碼只能看、不能改。
- 模組開關：每個模組附一句說明，關閉前要確認，並提示「資料會保留，重新開啟即可恢復」。

## 品牌

- 左上角顯示教室 logo，沒有 logo 時顯示教室名稱；登入頁與頁尾保留小字「MUP」。
- 週課表匯出圖片原本寫死黑嘉嘉圍棋 logo 與「大雅分校」（`WeeklyTimetableGrid.tsx`），改成讀取教室的 logo 與名稱。
- 程式中其他寫死的教室專屬字樣也一併盤點替換，列在各階段計畫中。

## 分階段

| 階段 | 內容 | 可見改變 |
|---|---|---|
| 一、教室隔離 | Classroom 表、47 表加 `classroomId`、統一過濾器與 guard、登入改三欄、原生 SQL 修正、排程逐教室執行、Storage 路徑、正式站搬遷 SQL | 登入多一欄教室代碼 |
| 二、平台後台 | PlatformAdmin、`/platform` 登入與後台、停用機制 | 僅平台管理員可見 |
| 三、模組與品牌 | 模組開關（選單、頁面、API、跨模組區塊、排程）、教室設定頁、教室 logo 與名稱、課表匯出品牌 | 行政可開關功能、左上角換成教室 logo |

每個階段各自寫一份實作計畫。先寫第一階段。

## 正式站搬遷（第一階段上線）

1. 備份整個資料庫（Supabase 備份或 `pg_dump`）。
2. 作者在 Supabase SQL Editor 執行搬遷 SQL（要能冪等）：
   - 建立 `Classroom`，並插入現有教室（代碼 `hjjdaya`）。
   - 各表加 `classroomId` 欄位（先允許 null）→ 全部回填成現有教室 → 改為 NOT NULL → 建外鍵與索引 → 更換唯一鍵。
3. SQL 跑完後再 push 程式，趁非上課時段進行。
4. 所有使用者重新登入。事先通知家長與老師，並提供 `/login?c=<代碼>` 連結。
5. 若出現嚴重問題：還原備份並回退程式。

## 測試

1. **結構守門**：自動測試讀取 Prisma DMMF，斷言除了白名單（`Classroom`、`PlatformAdmin`）以外，每個 model 都有 `classroomId`。
2. **跨教室隔離**：建立 A、B 兩間教室的資料，對各 API 群組驗證 A 的 session 讀不到、也改不到 B 的資料（列表、單筆、更新、刪除都要測）。
3. **fail-closed**：沒有教室情境時查詢租戶 model 必須拋錯。
4. **現有測試全部通過**：測試 fixture 預設在一間教室的情境下執行。
5. **登入**：代碼錯、帳號錯、密碼錯的訊息一致；教室停用；`?c=` 預填；跨教室同 email 各自登入。
6. **效能**：搬遷前後，以正式站等級的資料量量測學生管理、點名、收費清單的回應時間。

## 不在範圍內

- 自助註冊、訂閱與金流、訂閱等級。
- 一個帳號跨多間教室（資料結構不排斥，以後可以加一張 membership 表）。
- 總校／分校階層。
- 平台管理員進入教室協助排錯、稽核紀錄。
- 模組名稱自訂、細部規則設定（補課期別、點數比例等）。
