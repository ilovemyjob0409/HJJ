# 櫃檯報到（條碼掃描）— 選課畫面與比對邏輯改版 設計文件

日期：2026-07-29

## 背景與目標

現有設計（見 [`2026-07-28-kiosk-checkin-design.md`](2026-07-28-kiosk-checkin-design.md)）用「60 分鐘時間窗」自動判斷一次掃描要對應哪一堂課。實際拿實體掃描器測試時出現掃碼後「找不到可報到的課程」的情況，即使該生看起來確實有課在附近時段；根本原因目前尚未查出，但時間窗本身就是最可疑的一環——它同時扮演「限制」與「消歧」兩種角色，任何時鐘、時區或邊界值的細節落差，都可能讓一個原本合法的候選被濾掉，導致找不到任何候選。

時間窗也造成真實使用上的摩擦：有些學生會提早（例如上課前 2 小時）到櫃檯，此時系統還不讓他報到。

這次改版目標：拿掉時間窗，改用「候選堂數」決定要不要問學生——不需要選的情況維持零互動，只有真的有多堂候選時才跳出畫面讓學生自己點。

## 範圍外

沿用 2026-07-28 文件的範圍外：弈廳／活動報到、學號批次匯入、聲音／燈光回饋、非管理員登入的公開頁面。

另外本次不處理：原始 NO_SESSION 回報是否徹底根除。拿掉時間窗排除了「窗口本身濾掉合法候選」這個嫌疑最大的成因，但如果現場重測後仍有問題，需要另外一輪除錯，不在本次改版範圍內。

## 比對邏輯（取代原本 3-tier 時間窗邏輯）

對於掃描到的學號，先算出「今天的候選場次」——查詢方式不變：該生今天星期幾對應的已 enroll 班級課、今天核准插班的班級課、今天核准的一對一補課，並扣掉今天核准請假的班級。

依現有點名紀錄把候選分成兩組：

- **未完成**：還沒簽到，或已簽到但未簽退
- **已完成**：簽到、簽退都已填

判斷規則：

- **未完成 = 0** → 回傳 `NO_SESSION`（今天該生所有候選都已完成。若需要更正時間，行政人員改用一般點名頁面——該頁面已經支援把狀態改回「未點名」、清空簽到退時間，是這次一起上線的另一項修正）
- **未完成 = 1** → 直接自動判斷，不再檢查任何時間窗：該候選還沒簽到 → 這次掃描視為簽到；已簽到未簽退 → 這次掃描視為簽退。不管是提早 2 小時到、還是延後才簽退，都適用。
- **未完成 ≥ 2** → 回傳新的 `CHOOSE_SESSION` 結果，附上這些候選的清單，交由畫面顯示選課列表，等使用者點選其中一個後才寫入。

**行為差異提醒**：原本設計裡「已簽到未簽退」的候選永遠優先勝出，不會跳出選擇。這次改版後，如果同時有一個已簽到未簽退、一個還沒簽到的候選，未完成數 = 2，會改成跳出選課畫面讓使用者自己確認——是要簽退那一堂，還是簽到另一堂——不再由系統自動假設。

## 選課畫面資料

每個候選項目顯示：

- **課程名稱**：班級課（含插班）用班名；一對一補課固定顯示「一對一補課」
- **時間**：班級課用該班上課時間；一對一補課用該次補課的時間
- **老師名字**：班級課／插班用該班老師；一對一補課用該次補課指定的老師；查無則不顯示這一行
- **待執行動作標籤**：「待簽到」（尚未簽到）或「待簽退」（已簽到未簽退）

## API

`POST /api/attendance/checkin`（沿用既有路徑與權限：僅 ADMIN）

- Body 不變：`{ code, date, time }`
- Response 新增一種結果：
  ```
  { result: 'CHOOSE_SESSION', studentName, candidates: [
      { key, title, timeLabel, teacherName?, pendingAction: 'CHECK_IN' | 'CHECK_OUT' }
    ] }
  ```
  `key` 是不透明字串，前端不解析，只需要原封不動帶回下一個請求。

`POST /api/attendance/checkin/resolve`（新增，權限同上）

- Body：`{ code, date, time, key }`——重新用 code 找學生、重新算一次候選清單，確認 key 對應的候選仍然合法（防止選課畫面顯示期間資料被改掉，例如中途被加了一筆請假），再對那一個候選套用簽到／簽退邏輯
- Response 與原本 `/checkin` 的終態回應格式相同（`CHECKED_IN` / `CHECKED_OUT` / `NO_SESSION`——如果 key 已經失效）
- 不做 session／ticket 之類的伺服器端暫存，前端只要把上次拿到的 code 和選到的 key 原樣送回即可，維持無狀態

## 介面設計

沿用「B·卡片式」視覺方向（已與使用者用 mockup 確認）：置中卡片、深色漸層背景、品牌琥珀色重點色，維持「掃了就有反應、不用點任何東西」為預設路徑，選課只在真的有多堂候選時才出現。

四種畫面狀態：

- **待機**：卡片內一個琥珀色圓形圖示 + 「請將學生證放在掃描器前」+ 副標「掃描後會自動判斷今天的課程」
- **成功**（簽到、簽退共用同一種樣式）：綠色打勾圖示 + 「{學生名} 已簽到／已簽退 {時間}」+ 副標課程名稱
- **失敗**：紅色叉號圖示 + 對應錯誤訊息（查無學號／找不到可報到的課程／系統錯誤）
- **選課**（新增）：「{學生名}，請選一堂課」+ 副標「15 秒內未選擇將自動返回待機畫面」+ 候選列表，每列課程名／時間／老師 + 待簽到或待簽退標籤，點擊後呼叫 resolve

動效：沿用既有 `.animate-fade-in` / `.animate-rise-in`，不新增動畫關鍵影格（維持專案既有「重用既有 animate-\* class、不另創動畫」慣例）。不做圖示常駐呼吸動畫——mockup 比稿時的脈動效果只是為了展示活潑感，正式實作改用既有的進場淡入取代。

選課畫面 15 秒無操作自動回到待機（比原本結果訊息的 4 秒久，因為這次需要人做決定）；期間若又有新的一次掃描，直接以新掃描重啟流程，蓋掉正在等待的選課狀態。候選按鈕第一次點擊後立即停用，避免連點兩次送出兩次 resolve。

## 測試

`checkInByStudentNumber`／新的候選判斷邏輯走既有 Vitest + 真實測試資料庫慣例，覆蓋：

- 候選 0 個 → `NO_SESSION`
- 候選 1 個、尚未簽到 → 直接簽到，不限時間（含「上課前 2 小時」情境）
- 候選 1 個、已簽到未簽退 → 直接簽退，不限時間
- 候選 2 個以上 → 回傳 `CHOOSE_SESSION` 與正確的候選清單（含老師名字、待執行動作標籤）
- resolve：合法 key → 正確寫入；key 已經不在候選清單中（例如中途被請假排除）→ 安全回退成 `NO_SESSION`

API 路由與頁面比照本專案慣例（零路由測試、零元件測試），靠 `tsc --noEmit` + `eslint` + 瀏覽器手動驗證。
